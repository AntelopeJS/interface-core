## Overview

`@antelopejs/interface-core/modules` exports the lifecycle events and the management functions of AntelopeJS modules. A module moves through a fixed lifecycle, and each step emits an event that other modules can observe.

## Inspect the running modules

These functions work in a running AntelopeJS module, where the core has attached their implementations. This example reads each module's status and changes nothing.

```ts docs-check
import { ListModules, GetModuleInfo } from "@antelopejs/interface-core/modules";

for (const id of await ListModules()) {
  const info = await GetModuleInfo(id);
  console.log(id, info.status);
}
```

The [management functions](#management-functions) change what is running now. The [declaration functions](#declaration-functions) edit what the project loads on its next start. Neither kind calls the other.

## Import

```ts
import {
  Events,
  ListModules,
  GetModuleInfo,
  LoadModule,
  StartModule,
  StopModule,
  DestroyModule,
  ReloadModule,
} from "@antelopejs/interface-core/modules";
```

## Module lifecycle

A module moves through these states:

```text
loaded -> constructed -> active -> constructed -> loaded
                                   (stopped)     (destroyed)
```

| State         | Description                                    |
| ------------- | ---------------------------------------------- |
| `loaded`      | Module code is loaded but no instance exists   |
| `constructed` | Module instance is created but not started     |
| `active`      | Module is fully started and providing services |
| `unknown`     | Module status cannot be determined             |

## Module execution context

The module execution context matters to loaders. An application module receives its context from the runtime and does not make up its own owner IDs.

`RunWithModuleContext` carries module ownership through synchronous and asynchronous work:

```ts fragment
import { RunWithModuleContext } from "@antelopejs/interface-core/modules";

await RunWithModuleContext(
  {
    module: "search-provider",
    owner: "search-provider#42",
  },
  () => constructModule(),
);
```

`module` is the stable public module ID. `owner` names one lifecycle generation and defaults to the module ID. Give each generation a unique `owner` when an old and a replacement instance can run at the same time. `kind` is `"module"` by default. The core sets `"interface"` on the context it evaluates an interface package in. A provider callback runs in the context it was attached in, unless that context is of kind `"interface"`. `GetModuleContext` returns the active context, or `undefined` when there is none. It throws `ModuleContextInvalidatedError` once the context's owner is destroyed.

## Lifecycle events

The `Events` namespace exposes six `EventProxy` instances. Four fire for one module and pass its ID. `ModulesStarted` and `ModulesStopping` fire for the whole project and pass no argument.

### `Events.ModuleConstructed`

Fires after a module instance is created, before the module is started.

```ts
import { Events } from "@antelopejs/interface-core/modules";

Events.ModuleConstructed.register((moduleId: string) => {
  console.log(`Module constructed: ${moduleId}`);
});
```

### `Events.ModuleStarted`

Fires after a module's start method has completed. The module is then fully operational.

```ts
import { Events } from "@antelopejs/interface-core/modules";

Events.ModuleStarted.register((moduleId: string) => {
  console.log(`Module started: ${moduleId}`);
});
```

### `Events.ModuleStopped`

Fires after a module has been stopped. The module instance still exists but is no longer active.

```ts
import { Events } from "@antelopejs/interface-core/modules";

Events.ModuleStopped.register((moduleId: string) => {
  console.log(`Module stopped: ${moduleId}`);
});
```

### `Events.ModuleDestroyed`

Fires after a module instance has been destroyed and its resources released. `interface-core` itself listens to this event to remove the proxy attachments, registrations, and event handlers of the destroyed module.

```ts
import { Events } from "@antelopejs/interface-core/modules";

Events.ModuleDestroyed.register((moduleId: string) => {
  console.log(`Module destroyed: ${moduleId}`);
});
```

These four events pass the module ID. When `ModuleDestroyed` is emitted inside a `RunWithModuleContext` context of the same module, cleanup targets that context's `owner`. Otherwise cleanup targets the owner whose name is the module ID.

### `Events.ModulesStarted`

Fires once every module the core was asked to start has started, so the whole project is ready to serve. It does not fire when a module fails to start.

```ts
import { Events } from "@antelopejs/interface-core/modules";

Events.ModulesStarted.register(() => {
  console.log("All modules started");
});
```

### `Events.ModulesStopping`

Fires before the first module stops, once per stop that follows `ModulesStarted`. Stopping a project and reloading one module each count as a single stop.

```ts
import { Events } from "@antelopejs/interface-core/modules";

Events.ModulesStopping.register(() => {
  console.log("Modules are stopping");
});
```

## Management functions

These functions are `InterfaceFunction` declarations. They work once the core runtime provides their implementation.

### `ListModules`

Returns the identifiers of all loaded modules.

```ts
import { ListModules } from "@antelopejs/interface-core/modules";

const modules = await ListModules();
// ["auth-module", "database-module", "api-module"]
```

### `GetModuleInfo`

Returns the information of one module, including its configuration, status, and file system path.

```ts
import { GetModuleInfo } from "@antelopejs/interface-core/modules";
import type { ModuleInfo } from "@antelopejs/interface-core/modules";

const info: ModuleInfo = await GetModuleInfo("auth-module");
// info.status -> "active"
// info.localPath -> "/path/to/auth-module"
// info.source -> { type: "package", ... }
```

### `LoadModule`

Loads a new module with the given configuration. With `autostart` set to `true`, the module also starts after it loads. `autostart` defaults to `false`.

```ts
import { LoadModule } from "@antelopejs/interface-core/modules";
import type { ModuleDefinition } from "@antelopejs/interface-core/modules";

const definition: ModuleDefinition = {
  source: { type: "package", package: "@my/module", version: "1.0.0" },
  config: { key: "value" },
};

await LoadModule("my-module", definition, true);
```

### `StartModule`

Starts a loaded but inactive module. It does nothing if the module is already active.

```ts
import { StartModule } from "@antelopejs/interface-core/modules";

await StartModule("my-module");
```

### `StopModule`

Stops an active module. The module instance stays and stops providing services. It does nothing if the module is not active.

```ts
import { StopModule } from "@antelopejs/interface-core/modules";

await StopModule("my-module");
```

### `DestroyModule`

Destroys a stopped module instance. The module code stays loaded.

```ts
import { DestroyModule } from "@antelopejs/interface-core/modules";

await DestroyModule("my-module");
```

### `ReloadModule`

Stops and destroys a module if needed, unloads its code, and loads it again from its source. A module update then needs no restart of the whole application.

```ts
import { ReloadModule } from "@antelopejs/interface-core/modules";

await ReloadModule("my-module");
```

## Declaration functions

These functions read and edit the `modules` of the project's `antelope.config.ts`. They serve a module that installs or removes other modules and needs the change to survive a restart.

### `ListModuleDeclarations`

Returns the modules that the configuration file declares at its top level, by key. Shorthand entries come back expanded, and disabled modules are included.

```ts
import { ListModuleDeclarations } from "@antelopejs/interface-core/modules";

const declarations = await ListModuleDeclarations();
```

### `SaveModuleDeclaration`

Writes the given fields of a module's entry and adds the entry when the file has none. It rewrites only those fields. Every other line of the file stays as it was, comments and expressions included. A field set to `undefined` or `null` is removed. The running project does not restart for this write, so the caller loads, stops, or reloads the module itself.

```ts fragment
await LoadModule("@acme/reports", { source }, true);
await SaveModuleDeclaration("@acme/reports", { source, optional: true });
```

It throws when the file has no `modules` object it can edit, such as a configuration built by a function.

### `RemoveModuleDeclaration`

Removes a module's entry. The rest of the file stays as it was, and the project keeps running.

```ts
import { RemoveModuleDeclaration } from "@antelopejs/interface-core/modules";

await RemoveModuleDeclaration("@acme/reports");
```

## `ModuleDefinition`

The configuration object for defining a module.

| Property          | Type                       | Description                                            |
| ----------------- | -------------------------- | ------------------------------------------------------ |
| `source`          | `ModuleDefinitionSource`   | Source location and loading mechanism                  |
| `config`          | `unknown`                  | Optional configuration data for the module             |
| `importOverrides` | `Record<string, string[]>` | Optional runtime import override map with array values |
| `disabledExports` | `string[]`                 | Optional list of exports to hide from this module      |

`source` is a `ModuleDefinitionSource`. It has a `type` string that names the loader, with `"local"`, `"git"`, `"package"`, and `"local-folder"` built in. It also takes an optional `id` and `ignoreCache`, and the optional fields of those four kinds, such as `path`, `remote`, `package`, `version`, and `watchDir`. A field outside that set is a type error. A source with only a `type` is accepted.

`ModuleDefinition` is the runtime management contract of `LoadModule` and `GetModuleInfo`. It is not the project-file `AntelopeModuleConfig`, which uses `ImportOverride[] | Record<string, string>` for declarative provider bindings and named connections. The two `importOverrides` shapes differ on purpose. Do not copy one into the other or cast between them. `SaveModuleDeclaration` uses the project-file shape, described in [project configuration](./7.configuration.md#antelopemoduleconfig).

## `ModuleInfo`

`ModuleInfo` is `Required<ModuleDefinition>` with runtime information added, so every `ModuleDefinition` field is present.

| Property    | Type                                                 | Description                              |
| ----------- | ---------------------------------------------------- | ---------------------------------------- |
| `status`    | `"loaded" \| "constructed" \| "active" \| "unknown"` | Current lifecycle state of the module    |
| `localPath` | `string`                                             | File system path where the module exists |
